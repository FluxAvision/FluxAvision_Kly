## 1. 全景概述

### 一句话流程

```
人经过摄像头 → 摄像头感知到人数变化 → SDK TCP 推送事件到系统
  → 事件进入队列 → 消费线程处理 → 更新内存状态 → 写入数据库
  → 前端轮询 API 读取 → 展示在仪表盘/大屏
```

### 三个角色

| 角色 | 做什么 | 谁控制 |
|------|--------|--------|
| **大华摄像头** | 运行客流分析算法，检测到进出变化就推送给 SDK | 大华设备自身 |
| **SDK 网关层** | 维持 TCP 连接，接收推送，解析 C 结构体为 Python 对象 | SDK 内部线程 |
| **应用层管家** | 从队列消费数据、更新内存、写 DB、处理重连 | Python 消费线程 |

### 四个数据表

| 表 | 数据粒度 | 写入频率 | 用途 |
|----|----------|----------|------|
| TrafficCumulative | 每个设备一条，累计值 | 每 3 秒 | 实时仪表盘当日/累计进出 |
| TrafficHourly | 每个设备每小时一条 | 每整点切换时 | 小时报表、去重估算 |
| TrafficDaily | 每个设备每天一条 | 每天零时 | 日报表、历史趋势 |
| TrafficRecord | 每个设备每小时一条（原始增量） | 每 2 秒批量 flush | 原始数据追溯、历史查询 |

## 2. Step 1: 设备添加与注册

### 输入
用户在 Web 页面提交表单，包含：
- **必填**：设备名称、IP 地址、序列号
- **选填**：SDK 端口（默认 37777）、通道号（默认 0）、用户名（默认 admin）、密码

### 处理流程
1. 后端收到请求后，校验必填字段是否完整
2. 自动生成 RTSP 视频流地址（用于视频预览，与客流采集无关）
3. 将设备信息写入 `devices` 表，密码使用 AES-256-CBC 加密存储
4. 如果序列号已存在，返回 409 冲突错误
5. **设备模型为"大华"时**，自动触发客流采集启动

### 输出
- `devices` 表新增一行设备记录，status 字段初始为 `"offline"`
- 后台立即开始尝试连接设备（无需手动点击"开始采集"）

### 触发条件
- 用户通过 Web UI 添加大华设备
- 或通过 POST /api/devices API 直接调用

### ❗ 关注点
- 设备刚添加时密码以加密形式存入数据库，后续采集时解密使用
- 采集启动是异步后台线程，不影响 HTTP 响应速度
- 如果连接失败，不会阻塞设备创建流程，采集会在后台自动重试

## 3. Step 2: 系统启动与采集初始化

### 场景一：应用进程启动

系统启动时（FastAPI lifespan 事件），自动执行以下操作：

1. 遍历 `devices` 表，筛选出 `model = "大华"` 的所有设备
2. 对每台设备调用采集启动逻辑
3. 每台设备都在独立的后台线程中运行，互不干扰

### 场景二：用户在运行中添加设备

用户在系统运行中添加新的大华设备时，采集启动是同步触发但在后台执行的：
- HTTP 请求返回 201 Created 给前端
- 后台线程开始尝试连接设备

### 场景三：设备重启/断线后恢复

采集线程因异常退出后，由应用层重连循环自动恢复（详见 Step 8）。

### 输出
- 每台大华设备对应一个后台守护线程
- 状态迁移：`not_started` → `connecting` → `connected` / `reconnecting`

## 4. Step 3: SDK 初始化与连接设备

### 输入
- 设备 IP、端口（默认 37777）、用户名、明文密码
- 通道号（客流统计业务在哪个通道）

### 处理流程

SDK 初始化阶段按顺序执行以下关键动作：

1. **创建 SDK 实例** — 实例化底层 TCP 通信库
2. **注册断线回调** — SDK 检测到 TCP 断开时触发，仅记录日志，不做重连逻辑
3. **调用 InitEx 初始化 SDK 环境** — 传入断线回调函数和初始化参数结构体。如果失败，抛出异常终止连接
4. **注册重连回调** — SDK 内部自动重连成功后触发，回调中会重新订阅客流事件
5. **启用 SDK 自动重连** — 调用 SetAutoReconnect 接口，告诉 SDK 在连接断开后自动尝试恢复 TCP 连接

### 输出
- SDK 底层环境就绪，断线/重连回调已注册
- 如果 SDK 初始化失败（如 DLL 未找到、版本不兼容），抛出 RuntimeError

### 此时状态
- TCP 连接尚未建立
- 设备还没有登录

### ❗ 关注点
- 断线回调和重连回调是 SDK 层的回调，在 SDK 内部线程中执行
- 重连回调中会尝试重新 `_subscribe()`，如果订阅失败（设备未就绪），仅记录错误不影响重连循环
- 回调函数必须防止被 Python GC 回收，否则会导致段错误

## 5. Step 4: 登录设备

### 输入
- IP 地址、SDK 端口（37777）、用户名、密码
- 登录模式：TCP 直连（非 UDP 或 HTTP 代理模式）

### 处理流程
1. 调用 SDK 的 LoginEx2 接口，传入上述参数
2. SDK 与设备建立 TCP 连接并进行身份认证
3. 认证成功返回 `login_id`（登录句柄），用于后续所有 API 调用
4. 认证失败返回 0，并抛出 ConnectionError

### 输出
- `login_id`（登录句柄）保存在内存中，后续订阅/注销都用这个句柄
- 设备状态开始变为 `"online"`

### ❗ 关注点
- 如果密码错误或设备网络不通，LoginEx2 在几秒内返回失败
- 登录失败由应用层重连循环统一处理（指数退避重试）
- 系统停止采集时调用 Logout 释放句柄

## 6. Step 5: 订阅客流事件

### 三种数据获取模式

系统支持三种模式，通过 `mode` 参数选择。其中 **VideoStat 是默认且推荐的模式**。

### 模式一：VideoStat（推荐，纯人数统计）

**工作方式**
- SDK 调用 `AttachVideoStatSummary` 接口
- 摄像头主动推送客流统计汇总数据
- **每次检测到进出人数变化就触发一次回调**

**回调数据包含**
- 累计进入/离开数（设备上电以来的累计值）
- 今日进入/离开数（设备今日 00:00 以来的累计值）
- 近 1 小时进入/离开数
- 当前在场人数
- 通道号、规则名称

**特点**
- ✅ 稳定高效，SDK 原生支持，无额外配置
- ❌ 不包含年龄、性别、口罩等属性信息
- 回调频率：客流密集时约每秒 1-3 次

### 模式二：IVS NUMBERSTAT（智能分析事件）

**工作方式**
- 调用 `RealLoadPictureEx` 监听 NUMBERSTAT 类型事件
- 同样只推送人数统计，不包含人脸属性

**回调数据包含**
- 区域人数、进入数、离开数、通过数、上限值

**特点**
- 需要摄像头开启 IVS 智能分析功能
- 数据格式略有不同，但业务处理逻辑相同
- 作为 VideoStat 不可用时的备选方案

### 模式三：FACEDETECT（含年龄性别的人脸检测）

**工作方式**
- 调用 `RealLoadPictureEx` 监听 FACEDETECT 类型事件
- 每检测到一张人脸触发一次回调

**回调数据包含**
- 性别（male/female/unknown）
- 精确年龄和年龄段（baby/child/youth/middle/old）
- 口罩状态、眼睛状态、嘴巴状态
- 魅力值（1-100）、人脸质量分（0-10000）

**特点**
- ✅ 提供更丰富的人群画像数据
- ❌ 需要摄像头开启"人脸检测"智能分析规则（在摄像头 Web 管理界面配置）
- ❌ 数据量更大（每人脸一次回调），队列压力更高
- ❌ 回调频率更高，对消费端处理能力要求更高

### 输出
- SDK 收到订阅成功的句柄（attach_handle / ivs_handle / face_handle）
- 摄像头开始向系统推送数据
- 后续数据通过回调函数 `_cb` 进入系统

### 关键设计点：队列缓冲

回调函数内部做了什么：
1. 解析 SDK 原始数据（C 结构体 → Python 数据对象）
2. 创建 `PeopleFlowSnapshot` 或 `FaceRecord` 数据对象
3. 调用 `put_nowait()` 放入队列
4. **队列满时不阻塞回调**（避免阻塞 SDK 内部线程）

队列容量配置：
- 人流队列（PeopleFlowSnapshot）：最大 500 条
- 人脸队列（FaceRecord）：最大 2000 条

## 7. Step 6: 数据回调与分发（关键延迟点）

这是整个链路中**最关键也最复杂的环节**。从 SDK 回调触发到数据写入数据库，经过层级化的处理。

### 7.1 第一层：SDK 回调 → 队列（SDK 内部线程）

```
SDK 检测到人数变化
  → SDK 内部线程调用 _cb 回调函数
  → 解析 NET_VIDEOSTAT_SUMMARY 结构体
  → 创建 PeopleFlowSnapshot 对象
  → put_nowait() 放入 _flow_queue
```

此阶段在 SDK 内部线程中执行，必须**快速返回**，不能阻塞。

### 7.2 第二层：消费线程取队列 → 分发（守护线程）

```
独立守护线程（每设备一个）
  → 循环从队列取数据
     ├─ get(timeout=0.01) 取人流数据
     ├─ get(timeout=0.01) 取人脸数据
     └─ 队列空时 sleep(0.002) 降低 CPU
  → 调用 on_flow_update(snap) 或 on_face_detected(face)
  → 记录处理耗时日志（>100ms 打印警告）
```

### 7.3 第三层：`on_flow_update` 处理（应用层核心逻辑，分两个阶段）

#### 阶段 A：锁内更新内存（微秒级，快速）

加锁 `self._lock`，在锁内完成：

1. **检测日期变化** — 与内存中的 `today_date` 比较，如果日期变了：
   - 调用小时统计结算（将上小时的统计数据写入 DB）
   - 调用日统计结算（将昨天的数据汇总写入 DB）
   - 重置当日累计值
2. **检测小时变化** — 与内存中的 `current_hour` 比较，如果小时变了：
   - 调用小时统计结算
   - 重置小时累计和在场采样数据
3. **计算进出增量** — 记录上次的 `last_device_today_in/out`，与当前值相减得到 delta
   - 首次回调时delta=0（无历史基准值）
   - 后续回调每次计算出本次新增的进出人数
4. **更新内存状态** — 设备今日进出值、在场人数、小时累计进出、在场采样列表
5. **记录数据到本地变量**（在锁内获取到 delta_in/delta_out/日期/小时后，记录到临时变量供后续使用）

#### 阶段 B：锁外数据库写入（慢操作，节流）

**锁已释放**，在锁外执行耗时操作：

1. **累计统计写入**（TrafficCumulative）— 每 3 秒写一次
   - 使用 `time.monotonic()` 计时，距上次写入不足 3 秒则跳过本次写入
   - 写入时直接覆盖设备累计进出值和在场人数
   - 不判断数据是否变化：即使数值没变，到时间就写

2. **增量记录缓存**（TrafficRecord）— 每 2 秒批量写入
   - 只缓存有增量（delta_in>0 或 delta_out>0）的数据
   - 按 `(deviceId, date, hour)` 为 key 聚合缓存
   - 距上次 flush 满 2 秒时批量写入：一次事务写入该设备的所有待 flush 记录
   - 设备停止时强制 flush 确保不丢数据

3. **定期日志输出** — 每 5 分钟记录一次当前的客流统计摘要

### ❗ 延迟关键点一：原设计缺陷

**之前的设计（已修复）** 中，阶段 A 和阶段 B 都在同一个锁内完成，意味着：

```
SDK 回调 → on_flow_update → 加锁 → 内存更新 → 写 Cumulative DB → 写 Record DB → 解锁
                                                                    ↑
                                                            锁内 DB 操作 20-100ms
                                                                    ↑
                                                         下一次回调必须等待
```

在客流密集时，锁持有时间过长导致后续回调排队。这是之前延迟问题的**根本原因**。

### ✅ 优化方案（当前设计）

```
SDK 回调 → on_flow_update
  ├─ 加锁（<1μs）→ 内存状态更新 → 解锁（<1μs）← 极快返回
  └─ 锁外节流 DB 写
       ├─ Cumulative：每 3 秒一次（独立计时）
       └─ Record：每 2 秒批量 flush（合并多个增量写入一个事务）
```

### ❗ 延迟关键点二：队列空转

消费线程在双队列均空时 sleep(0.002) = 2ms。虽然时间很短，但在高要求场景下可以考虑事件通知机制替代轮询。

### 时序图

```
时间 →→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→

SDK 内部线程:    |—解析—|put_nowait|
消费线程:               |—get—|on_flow_update|
                               ↓
加锁:                        |⬛|       ← 微秒级
内存更新:                      |⬛|     ← 微秒级
解锁:                          |⬛|     ← 微秒级
                               ←——锁外——→
累计写(3s节流):                         |———DB写———|
增量写(2s批量):                          |———DB写———|
                                        ←——时间轴——→
```

## 8. Step 7: 数据持久化与报表结算

### 8.1 TrafficCumulative — 累计客流

| 项目 | 说明 |
|------|------|
| **写入时机** | 每 3 秒一次（节流），与回调频率解耦 |
| **数据内容** | 今日累计进入、今日累计离开、当前在场人数 |
| **写入方式** | 按 deviceId 查询 → 存在则 UPDATE，不存在则 INSERT |
| **用途** | 实时仪表盘展示"今日进店""今日离店""当前在场" |

### 8.2 TrafficHourly — 小时统计

#### 写入触发条件
- 系统检测到当前小时切换（如 10:00 → 11:00）
- 或系统检测到日期切换（同时结算上个小时 + 上一天）

#### 写入内容
- 该小时的累计进出数（原始值）
- **去重估算**：原始值 × 0.85 系数（非真实去重，估算值）
- 在场人数统计：该小时内所有回调中的在场人数的平均值、最大值、最小值
- 每台设备每小时一条记录

#### 数据来源
该小时内所有回调产生的增量累加（`hourly_entered`, `hourly_exited`）。

#### 去重算法说明
```
countInUnique = int(hourly_entered × 0.85)
countOutUnique = int(hourly_exited × 0.85)
```
系数 0.85 是经验值（假设 85% 为独立访客，15% 为重复进出）。
**这不是真正的去重**，真正的去重需要摄像头支持人脸识别或轨迹追踪。

### 8.3 TrafficDaily — 日统计

#### 写入触发条件
- 系统检测到日期切换

#### 写入内容
- 汇总当天所有 TrafficHourly 记录的 countIn/countOut 总和
- 去重值也汇总
- 当天在场人数的最大值和最小值

#### 数据来源
查询该设备当天的所有 TrafficHourly 记录，汇总计算。

### 8.4 TrafficRecord — 原始增量记录

#### 写入时机
- 每 2 秒批量 flush
- 仅在有进出增量时触发（delta_in>0 或 delta_out>0）

#### 写入方式
- 按 `(deviceId, date, hour)` 聚合缓存
- 批量 flush 时 upsert：有记录就累加增量，没有就新建
- 一次事务写入该设备的全部待 flush 记录

#### 用途
- 向后兼容已有的历史数据查询接口
- 提供比小时统计更细粒度的数据追溯

### 8.5 数据表关系全景

```
人经过摄像头
    ↓
SDK 回调 (每秒 1-3 次)
    ↓
内存增量计算 (delta_in, delta_out)
    ↓
  ┌─ 每 3 秒 ──→ TrafficCumulative（累计值，用于实时展示）
  │  写入方式：直接覆盖累计值
  │
  ├─ 每 2 秒 ──→ TrafficRecord（原始增量，用于历史追溯）
  │  写入方式：增量累加 upsert
  │
  ├─ 每小时切换 → TrafficHourly（小时统计，用于小时报表）
  │  写入方式：原始进出 + 去重估算 + 在场采样统计
  │  触发者：on_flow_update 中检测到 current_hour 变化
  │
  └─ 每天切换   → TrafficDaily（日统计，用于日报表）
     写入方式：汇总当天 TrafficHourly
     触发者：on_flow_update 中检测到 today_date 变化
     数据依赖：依赖 TrafficHourly 的完整性
```

### 8.6 数据流向图

```
                        TrafficRecord ←——每2秒缓存flush——┐
                                                         │
人 → 摄像头 → SDK → 队列 → on_flow_update → 内存更新      │
                          (锁内 微秒)        (增量计算)    │
                           ↓                               │
                    锁外(节流) ←———————— → → TrafficCumulative ← 每3秒节流
                           ↓
                    小时切换 → TrafficHourly
                           ↓
                    日期切换 → TrafficDaily (汇总TrafficHourly)
```

## 9. Step 8: 断线重连机制

系统采用**两层重连**设计，各自处理不同层面的故障。

### 9.1 第一层：SDK 层自动重连

| 项目 | 说明 |
|------|------|
| **触发条件** | SDK 检测到 TCP 连接断开（网络抖动、设备重启、路由器断开） |
| **重连频率** | SDK 内部控制，通常 5-30 秒 |
| **重连成功后** | 自动调用重连回调 `_rc`，回调中重新 `_subscribe()` 订阅事件 |
| **特点** | 完全自动，应用层无感；重连间隔 SDK 决定，不可自定义 |

### 9.2 第二层：应用层指数退避重连

| 项目 | 说明 |
|------|------|
| **触发条件** | SDK 登录失败、SDK 初始化失败、采集线程异常退出 |
| **重连策略** | 指数退避：3s → 6s → 12s → 24s → 30s（封顶） |
| **最大退避间隔** | 30 秒 |
| **重连成功后** | 创建全新的 DahuaPeopleCounter 实例（重新走 Step 3~6 全流程） |
| **特点** | 全面兜底，任何异常都能恢复 |

### 9.3 两层协作方式

```
场景 A：短暂网络抖动
  网络中断 → SDK 检测到 TCP 断开 → SDK 自动重连 → 重连成功
    → SDK 调用重连回调 → 重新订阅事件 → 恢复采集
    第一层搞定，第二层无感知

场景 B：设备重启（断电重启）
  设备断电 → SDK 检测到 TCP 断开 → SDK 自动重连（失败）
    → 采集线程内 catch 到异常
    → 第二层开始指数退避：等 3s → 重试 → 失败 → 等 6s → 重试 → ...
    → 设备恢复 → 登录成功 → 订阅成功 → 恢复采集

场景 C：持续不可用（设备离线数小时）
  → 第二层退避到 30s 封顶
  → 每 30s 尝试一次
  → 直到设备恢复或用户手动停止采集
```

### 9.4 断线后数据会不会丢？

**不会因为重连导致数据丢失**，原因如下：

- 客流数据是**累计值**（今日累计进/出），每次回调都携带设备当前的累计值
- 系统通过计算两次回调之间的**增量**（delta）来记录新增客流
- 断线期间产生的客流数据，摄像头自己会累加。重连成功后的第一次回调包含截止到当前的全部累计值，系统会自动计算从断线到重连之间的总增量
- 增量算法：`delta = current_value - last_recorded_value`。断线期间的值被一次性记录

**唯一可能丢失的场景**：系统进程崩溃（异常退出），尚未 flush 到数据库的缓存增量记录丢失。但这种情况概率极低且数据量极小（最多 2 秒的增量数据）。

## 10. 数据模型关系图

### 10.1 实体关系

```
devices (设备表)
  │
  ├── traffic_cumulative (累计客流, 1:1)
  │     每设备一条，按 deviceId 唯一关联
  │
  ├── traffic_hourly (小时统计, 1:N)
  │     每设备每小时一条，由 (deviceId, date, hour) 唯一标识
  │
  ├── traffic_daily (日统计, 1:N)
  │     每设备每天一条，由 (deviceId, date) 唯一标识
  │     数据来自对同一日 traffic_hourly 的汇总
  │
  └── traffic_records (原始增量, 1:N)
        每设备每小时一条（可多条），由 (deviceId, date, hour) 标识
        与前三个表的根本区别：存的是增量而非累计值
```

### 10.2 关键区别

| 对比维度 | Cumulative | Hourly | Daily | Record |
|----------|-----------|--------|-------|--------|
| **存储值类型** | 累计值（今日总数） | 时段累计 | 日累计 | 原始增量 |
| **每设备数据量** | 1 条 | 24 条/天 | 1 条/天 | 24 条/天 |
| **写入频率** | 每 3 秒 | 每整点 | 每天 | 每 2 秒批量 |
| **数据用途** | 实时展示 | 小时报表 | 日报表 | 历史追溯 |
| **是否可恢复** | 可(从设备重拉) | 可(重新结算) | 可(重新结算) | 不可(原始事件不可恢复) |

## 12. 延迟分析与优化历程

### 12.1 初始问题

在现场部署后发现，客流数据从人经过摄像头到显示在页面上有明显延迟（数秒级别）。排查发现延迟主要在数据处理链路中积累。

### 12.2 根因分析

#### 根因一：锁内数据库写入（最严重）

`on_flow_update` 持有 `self._lock` 期间同时执行了 DB 写入操作。每个 DB 写操作耗时 20-100ms。在客流密集场景（每秒 1-3 次回调），后续回调被锁阻塞排队，延迟不断累积。

#### 根因二：累计统计无节流写入

即使设备计数没有变化（delta_in=0, delta_out=0），每次回调都写 TrafficCumulative 表。在设备每秒上报 2-3 次的典型场景下，每小时产生 7200-10800 次无意义的 DB 写操作。

#### 根因三：增量记录即时写入

每次有进出事件时即时 upsert TrafficRecord。对于繁忙场景（频次高、每次 1-2 人），同样产生大量 DB 操作。

### 12.3 已实施的优化

| 优化项 | 效果 |
|--------|------|
| DB 写移出锁 | 锁保护范围缩小到纯内存操作（微秒级→微秒级） |
| 累计写入节流（3s） | 回调写入次数减少 90%+ |
| 增量批量 flush（2s） | 替代每次回调都写，写入次数减少 90%+ |
| 消费线程使用 blocking get | 替代 get_nowait+sleep，降低 CPU 空转，减少队列延迟 |

### 12.4 预期效果

- 优化前：事件从产生到入库延迟可能达数秒（锁排队 + DB 写阻塞）
- 优化后：事件从产生到写入队列 <1ms，队列到内存更新 <1ms，DB 写异步 2-3s 内完成
- **实时性瓶颈从数据处理转为数据库写入，而实时展示数据来自内存状态（秒级更新），用户感知延迟极低**

### 12.5 仍有优化空间的方向

| 方向 | 说明 | 优先级 |
|------|------|--------|
| SQLite → 其他 DB | 换用 PostgreSQL/MySQL 可大幅降低写入延迟 | 低（架构改动大） |
| 异步 DB 引擎 | 使用 aiosqlite 异步写入 | 低（收益有限） |
| 事件通知机制 | 队列空时用 threading.Event 替代轮询 | 低（当前 2ms 已经很低） |
| 实时性分离 | 实时展示直接从内存读取，DB 写入再延迟 1-2s | 已实现 |
| DB 连接池 | 引入连接池减少每次创建 session 开销 | 中 |

### 12.6 可观测性

系统已内置延迟日志：
- `on_flow_update` 处理耗时 > 100ms 时打印 WARNING 日志
- `on_face_detected` 处理耗时 > 50ms 时打印 WARNING 日志
- 日志格式包含当前进出值，方便定位是哪个设备、什么时刻

在生产环境中，可以通过监控这些日志快速发现延迟异常。
